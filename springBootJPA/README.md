# Spring Boot JPA: Deep Dive & Learnings

This module is designed to demonstrate how to handle complex database relationships and performance optimizations in a Spring Boot application using Spring Data JPA.

## Essential Setup & Monitoring
- **SQL Logging:** In `application.properties`, `spring.jpa.properties.hibernate.show_sql=true` is enabled. **Watch your console!** Every time you hit an endpoint, you can see if JPA is executing one query or many.
- **Batch Fetching:** `spring.jpa.properties.hibernate.default_batch_fetch_size=10` is active. This is a "safety net" that batches the loading of lazy associations.
- **H2 Console:** [http://localhost:8080/h2-console](http://localhost:8080/h2-console) (Use `jdbc:h2:mem:testdb` with no password). Use this to verify the table structures and data generated by `JavaFaker`.

## Endpoint-Wise Learning Guide

### 1. The "N+1" Solution (Profile Fetching)
**Endpoint:** `GET /customer/1/profile/{id}`

- **The Problem:** A standard `findById` would fetch the Customer, then a second query for the Profile (Lazy Loading).
- **The Feature:** Demonstrates **JPQL JOIN FETCH** vs **Interface Projections**.
- **Try it with Curl:**
  ```bash
  # Option A: JPQL Join Fetch (Fetches all columns of both entities in 1 query)
  curl "http://localhost:8080/customer/1/profile/1?key=true"

  # Option B: Projections (Fetches ONLY the columns needed for the DTO)
  curl "http://localhost:8080/customer/1/profile/1?key=false"
  ```
- **Learning:** 
    - Look at the console. With `key=true`, you'll see a `JOIN` in the SQL.
    - With `key=false`, you'll see `SELECT customer0_.id, profile1_.email...` (Selective columns). Projections are faster for read-only APIs.

### 2. JPQL vs Native Query (Deep Graph)
**Endpoint:** `GET /customer/2/profileOrder/{id}`

- **The Feature:** Fetching a 3-level hierarchy: **Customer -> Profile -> Orders**.
- **Try it with Curl:**
  ```bash
  # Forces JPQL execution
  curl "http://localhost:8080/customer/2/profileOrder/1?key=true"

  # Forces Native SQL execution
  curl "http://localhost:8080/customer/2/profileOrder/1?key=false"
  ```
- **Learning:**
    - **JPQL Challenge:** In `CustomerRepository.findCustomerProfileOrderData`, we use `LEFT JOIN FETCH`. Notice in the logs that Hibernate might still fetch "Payments" for those orders if not handled, because of the relationship mapping.
    - **Native Query Power:** The native query in `findCustomerProfileOrderDataNative` gives you absolute control. However, look at `CustomerService.java` — we have to manually map `Object[]` to `CustomerDto`. This is the "cost" of native queries.

### 3. Collection Filtering (Large Data Sets)
**Endpoint:** `GET /customer/3/profileOrder/{email}`

- **The Feature:** Searching across a join with `LIKE`.
- **Try it with Curl:**
  ```bash
  curl "http://localhost:8080/customer/3/profileOrder/gmail"
  ```
- **Learning:**
    - Demonstrates how to use `JOIN FETCH` with a collection (`orders`) while applying a filter on a joined entity (`profile`).
    - **Note:** Be careful with `JOIN FETCH` on multiple collections (Cartesian Product risk).

### 4. Advanced Aggregation (The HAVING Clause)
**Endpoints:** 
- `GET /customer/4/moreThanThreeOrders`
- `GET /customer/5/moreThanThreeSuccessfulOrders`

- **The Feature:** Using DB-level grouping and filtering.
- **Try it with Curl:**
  ```bash
  curl "http://localhost:8080/customer/4/moreThanThreeOrders"
  curl "http://localhost:8080/customer/5/moreThanThreeSuccessfulOrders"
  ```
- **Learning:**
    - `Endpoint 4` shows how to use `GROUP BY c HAVING COUNT(o) > 3` in JPQL. This moves the filtering logic from Java to the Database, which is much more efficient.
    - `Endpoint 5` goes deeper: `JOIN o.payment p WHERE p.paymentStatus = 'SUCCESS'`. It filters the *collection* before counting, demonstrating how to aggregate on nested properties.

### 5. Many-to-Many & Distinct Results
**Endpoint:** `GET /product/distinct-with-categories`

- **The Feature:** Handling the "Duplicate Parent" problem in Joins.
- **Try it with Curl:**
  ```bash
  curl "http://localhost:8080/product/distinct-with-categories"
  ```
- **Learning:**
    - When you join a Product with 3 Categories, SQL returns 3 rows for the same Product.
    - **JPQL `DISTINCT`:** Hibernate uses this keyword to filter those duplicates in the persistence context, so you get a `List<Product>` where each product is unique but contains its list of categories.

## Technical Learnings Summary

| Concept | Why it matters | Where to find in code |
| :--- | :--- | :--- |
| **N+1 Problem** | Prevents performance death by a thousand queries. | `CustomerRepository` (look for `JOIN FETCH`) |
| **Projections** | Reduces "Over-fetching" (don't fetch 50 columns if you need 3). | `CustomerRepository.findCustomersByIdProjections` |
| **Native Queries** | Best for performance-tuning or DB-specific features. | `CustomerRepository` (look for `nativeQuery = true`) |
| **Data Mapping** | Keeping Entities and DTOs separate for security and performance. | `util/DataMapper.java` |
| **Faker Seeding** | Instant testing with realistic data. | `SpringBootJpaApplication.java` |
| **Batch Size** | Emergency fix for lazy loading issues. | `application.properties` |
